- Commercial and Compliance pages were not re-checked as operations@ or finance@ beyond the listed probes.

## 2. Fix first (ranked)

1. **Employee reads the whole tenant through collection routes (P0 cluster, S1 to S5).** Add `assertScopeAll(resource,'view')` (precedent `apps/api/src/domains/books.ts:349-352`, defined `apps/api/src/platform/permissions.ts:531`) to: `listEmployments` (`domains/employment.ts:229`), `trialBalance` (`domains/compliance/books.ts:861`, route `routes/compliance/books.routes.ts:133`), `eInvoiceStatusList` (`domains/compliance/gst.ts:699`), `runLeaveYearClose` (`domains/compliance/labour.ts:190`), `runWeeklyHoursCheck` (`labour.ts:399`), and a create or edit verb in `computeAttribution` (`domains/marketing/attribution.ts:263`). Add one CI test that walks every GET as employee@ against an allowlist (S7).
2. **Map `ZodError` to 400 in `errorMiddleware`** (`apps/api/src/lib/http.ts:274-322`, insert before the 500 at `:321`). Return paths and messages only, never values. Also map `RangeError` from `money.ts` (`packages/shared/src/money.ts:131`) to 422. One change removes about 400 spurious 500s across about 66 bare `.parse(req.body)` calls.
3. **Hooks after early return crash three screens.** `apps/web/src/pages/Executive.tsx:320-321` returns before `useMemo` at `:323`, `:328`, `:348`; `apps/web/src/pages/marketing/Social.tsx:47-51` returns before `useMemo` at `:51`. Move the returns below the last hook. Add a loading-to-data render test.
4. **CreateModal has no in-flight guard.** `apps/web/src/components/forms.tsx:241-253`: add `if (mutation.isPending) return;` at the top of `run` and of the no-form `submit`. A `useRef` flag is safer, because `isPending` lags one render. Pair with idempotency keys on the creates that cost real money (invoice issue, quote create, convert).
5. **Invoice issue commits before the payment is taken.** `apps/api/src/domains/invoicing.ts:905` opens the invoice transaction and `:1003` calls `collectInvoicePayment` after it commits, so a 409 on the payment reference leaves an issued, unpaid invoice with a consumed GST number and a journal entry. Collect inside the transaction.
6. **Opportunity detail shows "₹NaN" on every deal.** `walk()` in `apps/api/src/platform/permissions.ts:685-722` copies a `Prisma.Decimal` field by field (`Object.entries`, `:692`), putting `{s,e,d}` on the wire. Return `v.toString()` for Decimals before the object branch. Fix the truthiness test at `apps/web/src/pages/Opportunities.tsx:232`.
7. **The CRM journey cannot be finished from the UI.** There is no create UI for proposal, quote, MoU or contract, and none for expected close date, expected value or organisation on an opportunity, so Qualified, Proposed and Won are unreachable (gates at `domains/opportunities.ts:407`, API at `routes/crm.routes.ts:1088`, `routes/commercial.routes.ts:190,432`). Add an edit card and "Create proposal / MoU" on `Opportunities.tsx` (the Commercial instruments card is near `:353`), plus "New quote" on the Quotes page.
8. **Approving a discount never lets the quote issue.** `domains/commercial.ts:742-751` recomputes `blockedLines` on every call without reading the approval step, and `:772` creates a new step each time. If the quote already has an open step, return it. If an approved step covers the current line discounts, issue.
9. **Duplicate and negative vendor bills.** `routes/books.routes.ts:262-282` takes `subtotal: z.number()` (negative accepted) and the model has only `@@unique([tenantId, recordCode])` (`apps/api/prisma/schema/main.prisma:5408`). Add a unique on (tenantId, vendorGstin or vendorName, billNumber) via migration, answer P2002 with 409, and use `.nonnegative().max()`.
10. **Privacy rights are broken for employees.** `routes/compliance/privacy.routes.ts:120` requires `personId` while the UI omits it, so an employee cannot raise an access or erasure request (500). Make it optional and default to `auth.personId` in `domains/compliance/privacy.ts:523`. Also scope `listDataRequests` (`privacy.ts:564-575`) by own person.

Also high on the list: GST summary counts voided invoices (`domains/books.ts:986`, use `notIn:['draft','void']`), and equity data-integrity bugs (fractional share counts, resolution without a meeting, AGM date).

### 4.1 Security and API

### [P0][VERIFIED] S1 Employee reads every employee (names, emails, status, division, confirmation state, joining date, transitions)

- Route: `GET /api/hr/employees`, `/people/employees`, role employee@. Dup: `09`, `06`.
- Repro: log in as employee@, call the route. 14 rows.
- Observed vs expected: full directory with `availableTransitions`; expected own row only or 403. The per-id route already 404s for other people (`hr.routes.ts:289`), so list and detail disagree.
- Root cause: `apps/api/src/domains/employment.ts:229` is `assertCan({resource:'employees',verb:'view'})` with no record. The seed gives employee `VE@own` (`apps/api/src/seed/grants.ts:978`), so the collection passes. `findMany` at `:231` filters by tenant only. Route maps all rows at `apps/api/src/routes/hr.routes.ts:266-283`.
- Fix: `assertScopeAll('employees','view')` for the collection, or narrow `where` to the caller's own relationship when scope is own (as payslips do, `compliance/payroll.ts:1062-1118`). Drop `confirmationState`, `hireEffectiveDate`, `availableTransitions` for non-HR scope. Test: employee@ gets only its own row.

### [P0][VERIFIED] S2 Employee reads the full trial balance (JSON and CSV)

- Route: `GET /api/compliance/books/trial-balance/:asOf`, role employee@.
- Observed vs expected: 200 with about 50 ledger accounts and totals; expected 403. The route audits an "export" afterwards, so the leak is recorded but not prevented.
- Root cause: no permission call in `apps/api/src/routes/compliance/books.routes.ts:133-146`, `domains/compliance/books.ts:861` (`trialBalance`) or `:874` (`trialBalanceCsv`).
- Fix: `assertScopeAll('transactions','view')` (or the ledger report verb) in the service so the period-close caller inside a tx is also covered. Audit refused attempts too.

### [P0][VERIFIED] S3 Employee reads CRM people PII, organisations and merge queue

- Routes: `GET /api/crm/people` (`routes/crm.routes.ts:88`), `/merge-candidates` (`:278`, returns `incomingPayload` with phone and email), `/organizations` (`:447`, via `listBodies` `:379`). Role employee@. Dup: `09`, `02`.

- Root cause: `people` is one resource covering staff directory, CRM contacts, students and merge queue; the seed grants it company-wide to employee (`seed/grants.ts:985`, comment "staff directory is a company-wide fact"). The route guards (`crm.routes.ts:91,280`) only check `people:view`. The organisations grant path was not traced (PLAUSIBLE for that sub-item).

## 6. Test-infrastructure notes

- **Login limiter** is 5 per minute per IP and per email (`apps/api/src/domains/compliance/corporate/rateLimit.ts:22-36`); 429 responses count, so retries extend the lockout. Every parallel QA agent shared one IP, and an office behind NAT would lock out together. Consider a higher per-IP limit (for example 30) while keeping 5 per email. The first run saturated it and blocked `02`, `05` and `07`.
- **Refresh tokens rotate**; the saved Playwright storageState holds one cookie and is not written back, so reuse reads as token reuse and kills the session (`03` lost chairman.json). Use the session helper (`auth/session.cjs`) and persist after each context. `/api/auth/logout` in an API sweep revokes the session (`09`).
- **employee@ has no employment record** in the seed (`06`: `users.personId` has 0 `employment_relationships`). Seed one so `/me/leave`, `/me/attendance` and `/me/payslips` can be tested.
- **"INV-POST TEST ONLY" accounts in the demo ledger are a real seed-path issue, not a QA artefact.** `package.json` `seed:demo` is `tsx src/tests/fixtures/run.ts` (`apps/api/package.json:34`), which calls `readyInvoicePosting(tenant.id)` on the `kaizen` tenant (`apps/api/src/tests/fixtures/run.ts:19`) and `scripts/test-db.sh:48` does the same for the suite DB. The fixture creates 16 accounts named `INV-POST TEST ONLY ...` and posting-role rows (`apps/api/src/tests/fixtures/invoicePostingReady.ts:62-91`), and its header says it is for "the demonstration tenant" on purpose. The plain `pnpm seed` writes no ledger accounts or posting roles (no `ledgerPostingRole` in `apps/api/src/seed`). So: (a) every invoice in the demo tenant posts to test-named accounts; (b) a non-demo tenant has no path to a usable chart and posting roles at all, and its first invoice issue is refused. Fix: a real chart-of-accounts and posting-role bootstrap in `seed/createTenant.ts` (ORDERED-PLAN item owner decides), rename fixture accounts for the demo, and keep the fixture only for suites that create their own tenants.
- Scheduler logs `jobs/marketing: skipping — messaging.dispatchQueuedSends is not exported yet` every tick (`apps/api/src/jobs/marketing.ts:62,118`); that job is silently skipped.
- Pool: 50 concurrent GETs serialise (p50 772 ms vs 15 to 50 ms single); check the DB pool size before any load test.
