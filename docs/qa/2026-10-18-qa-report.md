## 2. Fix first (ranked across both rounds)

1. **Account takeover through `POST /api/auth/sign-ins` with `reset: true` (P0, T1, VERIFIED by the orchestrator).** `routes/auth.routes.ts:238-250` calls `createOrResetSignIn` (`domains/signIns.ts:52-110`), which only asserts `holders:create` or `board_meetings:create` in the caller's tenant (`signIns.ts:46-53`). `ensureSignInPrincipal` (`lib/auth.ts:249-266`) then finds the Principal by email with `unscopedPrisma` across all tenants and, on reset, rotates its password and the caller receives it (`signIns.ts:105`). So any chairman or company secretary can reset and receive the password of any account in any tenant, including colleagues in their own. Because principals are global by email (`lib/auth.ts:428`), the new password opens every tenant that email belongs to. With `reset:false` it silently binds a new user in the caller's tenant to the foreign principal. Not run live (irreversible). Fix: refuse reset or link unless the principal has no users, or its only users are in the caller's tenant and linked to `input.personId`; never return a password for a pre-existing principal (use an out-of-band reset; the UI never sends `reset`, `Holders.tsx:273-325`, so nothing breaks, but see E16 for the needed safe path); audit refused attempts. Test: tenant B chairman posts tenant A's email with `reset:true`, expect 4xx and an unchanged `passwordHash`.
2. **Employee reads the whole tenant through collection routes (P0 cluster, S1 to S5, confirmed live again in `07`, `13`, `14`, in both tenants).** Add `assertScopeAll(resource,'view')` (precedent `apps/api/src/domains/books.ts:349-352`, defined `apps/api/src/platform/permissions.ts:531`) to: `listEmployments` (`domains/employment.ts:229`), `trialBalance` (`domains/compliance/books.ts:861`, route `routes/compliance/books.routes.ts:133`), `eInvoiceStatusList` (`domains/compliance/gst.ts:699`), `runLeaveYearClose` (`domains/compliance/labour.ts:190`), `runWeeklyHoursCheck` (`labour.ts:399`), and a create or edit verb in `computeAttribution` (`domains/marketing/attribution.ts:263`); split CRM contacts from the staff directory (S3). Add one CI test that walks every GET as employee@ against an allowlist (S7).
3. **Tenant creation writes into every other tenant, unscoped and unaudited (P1, T2).** `seed/bootstrap.ts:3022` calls `runBackfills()` (`seed/backfill.ts:205-219`) with no tenant argument; the four backfills use `unscopedPrisma` (owner role, bypasses RLS) and none calls `auditWrite`. Live: `tenant:create --slug acmeqa` created 12 `student_profiles` rows in kaizen and linked 15 kaizen users to principals. `backfillDesignations` (`backfill.ts:189-200`) matches any tenant's address that starts with `chairman@`. Rules 5 and 6 are both breached, on the path every new customer takes. Fix: pass `tenantId`, run under `asSystem(tenantId)`, audit, match the full address; keep the global run only as a one-off migration.
4. **A leave balance can be minted or lost through the API (P1, H7 to H10).** `days` is client-supplied and unbounded (`routes/hr.routes.ts:722`, `domains/leave.ts:322`), so `days:-5` credits 5 days on approval and `days:0` takes unrecorded leave; WITHDRAW posts a reversal for a request that was never approved (`packages/shared/src/hr.ts:217`, `leave.ts:426`); APPROVE never checks the balance (`leave.ts:367-440`), so a 27-day request against 11 days left the balance at -16; and "available" subtracts held days twice (`routes/hr.routes.ts:655`, `hcm/leavepolicy.ts:483,1270`). Fix: drop `days` from the create schema; post the reversal only from Approved, InProgress or Extended; lock the balance row and refuse APPROVE when `balanceDays < days`; `available = balanceDays`. Each needs a test that fails on the old code.
5. **Sessions outlive a password change, and the query cache outlives a sign-out (P1, A1, A2).** `changePassword` (`lib/auth.ts:614-634`) never touches `Session`, so an attacker's session survives the user's response to a suspected compromise. The `QueryClient` (`web main.tsx:268-272`) is never cleared and `signOut` (`lib/session.tsx:222-230`) does not clear it, so a second user on the same browser can see the first user's cached lists. Fix: revoke every other session of the principal inside `changePassword`; `queryClient.clear()` on sign-out and before adopting a user.
6. **The share register can be left half-written (P1, E14, E15, E1).** "Make effective" on an allotment writes `status:'effective'` (`domains/equity.ts:1172`) and then fails on the missing certificate signatories (`:1177`, `:1065-1073`), so the client is told 422 while the row is already effective with no certificate; transfers out of such a holder can then never be made effective (`:1224-1256`); a transfer from a holder to themselves is accepted (`:863`); and fractional share counts are accepted (`routes/equity.routes.ts:181`). Fix: check signatories before the update, or write both in one `governedWrite`; refuse equal holders; `.int()`; add a repair path for SHT-2026-00001, -00002, -00003 and -00007.
7. **CSV import corrupts dates, amounts and account class silently (P1, X1 to X3).** `31/02/2026` becomes 3 March (`imports/parse.ts:223-227`); amounts are JS numbers (`parse.ts:124`, `imports/commit.ts:2692`, `domains/books.ts:126`), so `12345678901234567890.99` becomes `12345678901234570000`; a card imported through the template lands in `ledgerGroup: asset` (`books.ts:128`, `commit.ts:2688-2695`) while the other import path gets liability right (`commit.ts:78`). Fix: round-trip the date parts; parse amounts to paise as `bigint` from the decimal string; derive card to liability in `createAccount`.

## 6. Test-infrastructure notes

- **Login limiter** (round 2 reread in `10`: A7) is 5 per minute per IP and per email (`apps/api/src/domains/compliance/corporate/rateLimit.ts:22-36`); 429 responses count, so retries extend the lockout. Every parallel QA agent shared one IP, and an office behind NAT would lock out together. Consider a higher per-IP limit (for example 30) while keeping 5 per email. The first run saturated it and blocked `02`, `05` and `07`.
- **Refresh tokens rotate**; the saved Playwright storageState holds one cookie and is not written back, so reuse reads as token reuse and kills the session (`03` lost chairman.json). Use the session helper (`auth/session.cjs`) and persist after each context. `/api/auth/logout` in an API sweep revokes the session (`09`).
- **employee@ and operations@ had no employment record** in the seed (`06`: `users.personId` has 0 `employment_relationships`). In round 2 both were hired through the app (`POST /hr/positions` with APPROVE_BUDGET and PUBLISH, `POST /hr/employees` with `personId` and `positionId` at `routes/hr.routes.ts:378-393` and `domains/employment.ts:372`, then ACTIVATE), employee@ got a ManagerChange assignment pointing at operations@ (leave approval resolves the manager through `assignment.managerPositionId`, `domains/hcm/leavepolicy.ts:832-841`; the chairman had to approve it because operations@ lacks `assignments:approve`), compensation (the proposer cannot approve) and accrued CL, SL and EL balances. No leave-policy assignment, attendance or payslip exists. Seed these for the demo tenant so the next round starts there.

Passwords are in `QA-ENV.md`, not in this report. Login needs no tenant slug (principals are global by email, the tenant comes from the user row), so use distinct emails per tenant. The session helper takes a full email for `@acmeqa.in` accounts. A new tenant has no ledger entity, and no API creates one (`domains/invoicePosting.ts:63`); invoicing was enabled with the test fixture `readyInvoicePosting`, which is the same thing `seed:demo` does for kaizen. `tenant:create` itself wrote into kaizen (T2): do not run it against a database whose first tenant matters.
- **The session helper hard-codes the demo password and `<tag>@kaizen.co.in`**, so a shareholder sign-in created in `11` could not be logged into (portal untested). Let the helper take an email and a password.
- **Every page says "set-up data is 1 build behind"** (`data #2`): the demo DB's seed lags the code. Grant-based findings (S1 to S5) were read in `seed/grants.ts` at HEAD, so they stand, but a reseed may change small details of the seeded states.

The fixture creates 16 accounts named `INV-POST TEST ONLY ...` and posting-role rows (`apps/api/src/tests/fixtures/invoicePostingReady.ts:62-91`), and its header says it is for "the demonstration tenant" on purpose. The plain `pnpm seed` writes no ledger accounts or posting roles (no `ledgerPostingRole` in `apps/api/src/seed`). So: (a) every invoice in the demo tenant posts to test-named accounts; (b) a non-demo tenant has no path to a usable chart and posting roles at all, and its first invoice issue is refused. Fix: a real chart-of-accounts and posting-role bootstrap in `seed/createTenant.ts` (ORDERED-PLAN item owner decides), rename fixture accounts for the demo, and keep the fixture only for suites that create their own tenants.
- Scheduler logs `jobs/marketing: skipping — messaging.dispatchQueuedSends is not exported yet` every tick (`apps/api/src/jobs/marketing.ts:62,118`); that job is silently skipped. Together with the unset `MARKETING_EMAIL_ADAPTER` (E-1), marketing dispatch has two blockers, and neither was cleared in round 2.
- Pool: 50 concurrent GETs serialise (p50 772 ms vs 15 to 50 ms single); check the DB pool size before any load test.
