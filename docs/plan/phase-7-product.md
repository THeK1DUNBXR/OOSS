# PHASE 7 — The product

**Duration:** three to four weeks.

- **Tenant onboarding as a resumable state machine**, not a script: provision → migrate schema → seed chart of accounts and statutory masters → configure (GSTIN, PAN, TAN, PF/ESI codes, PT local body, state labour rules, holiday calendar) → import openings → verify (the trial balance balances; a test IRN succeeds in the sandbox) → activate. Every step idempotent and resumable.
- **Statutory packs per state**, versioned, because PT slabs, minimum wages and state labour-code status change annually and your tenants span states.
- **Tiering.** Shared schema plus `tenant_id` plus RLS by default; a documented path to **database-per-tenant for enterprise tenants**. Given the Rule 3(5) India-residency requirement and DPDP per-principal erasure, a dedicated-database tier is a genuine sales asset — per-tenant point-in-time recovery and per-tenant export are far easier there.
- **Per-tenant encryption.** Envelope encryption, one DEK per tenant wrapped by a KMS CMK. This gives **cryptographic erasure**, which is a clean provable answer to a DPDP erasure request and to offboarding. ⚠️ It conflicts with the eight-year audit retention under s.128(5) — resolve deliberately by keeping the audit trail in a separately-keyed store with its own retention, and write the conflict into the contract. BYOK/CMK is a realistic enterprise upsell.
- **Noisy neighbour.** Per-tenant rate limits at the gateway; `statement_timeout` and per-tenant connection-pool caps; **separate pools and queues for interactive versus batch**, because payroll runs, GST return generation and month-end close are bursty and will starve the UI. Offload analytics off the OLTP primary entirely via CDC into a columnar store. Scale in this order: read replicas → partitioning by tenant or period → isolate the loudest tenants onto dedicated databases → shard **last**. Most platforms never shard.
- **India residency.** Rule 3(5) requires books in electronic mode to be backed up **daily on servers physically located in India**, and Rule 3(6) requires annual disclosure to the Registrar of the provider's name, address and location. So: `ap-south-1` (Mumbai) or Hyderabad, daily backups also in India, and a contractual statement your customers can hand to their ROC filing.
- **Static egress IPs** for IRP and e-way-bill whitelisting — a NAT gateway with fixed IPs, decided before Phase 3 ships.
- **A real API deployment.** `apps/api/Dockerfile` is genuinely production-shaped — multi-stage, `FROM base AS runtime`, `NODE_ENV=production`, running compiled `dist/server.js`. What is missing is a **host manifest**: no Kubernetes, no Fly/Render/Railway config, no systemd unit. And the only compose file commits `JWT_SECRET: docker-development-secret-not-for-production` (`docker-compose.yml:43`) and `OWNER_PASSWORD: kaizen2026` (`:51`) while setting `NODE_ENV: production`, which is the worst of both. The Cloudflare Worker story is honest about why the API cannot run on Workers (Prisma over TCP needs Hyperdrive, the scheduler is a `setInterval`, Express 4 is stream-based) but it leaves the server half undefined. Pick a host, write the manifest, wire it to CI.
- **Billing, plans, usage metering, a trial flow, and a signed data export on termination.**
